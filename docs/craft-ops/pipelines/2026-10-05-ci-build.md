# CI build — runs on `main` and on PRs

Greenfield pipeline design (no prior `.github/workflows`). Scope: build/test/lint
gate only — no deploy, no published artifact. Decided against `.craft-code.yml`'s
existing commands so CI runs exactly what a human already runs locally.

## Artifact strategy
No artifact is produced or stored. This pipeline's only output is a pass/fail
signal on a commit SHA — there is nothing to publish yet (single-player
desktop binary, no distribution channel decided). Revisit when `GDD.md` §11/§12
settles a release target.

## Stage ordering (fail fast, cheapest first — revised 2026-10-06)
1. `cargo fmt --check` — no compilation, fails in seconds.
2. `cargo build` — full codegen+link of the default target. Deliberately
   **before** clippy (see "Why clippy runs last" below).
3. `cargo test` — reuses `build`'s fully-linked dependency artifacts; only
   compiles the additional test binaries.
4. `cargo clippy --all-targets --all-features -- -D warnings` — runs **last**,
   not first.

**Why clippy runs last (corrected from the original design):** the original
version of this doc put clippy second on the "it's cheap, catches lint+type
errors early" theory. **Confirmed wrong by a real run** (PR #2, run
`37401768107`, 2026-10-06): `cargo clippy` runs Cargo in **check-mode**
(metadata-only, no codegen/link) for the *entire* dependency graph, not just
the local crate — it finished in ~4 min. The following `cargo test` step then
had to recompile **all 362 dependency crates from scratch in full build
mode** (confirmed via the job's own timestamped log, `unicode-ident` through
`bevy`/`red-rising`), taking ~19 of the job's ~23 total minutes. Check-mode
artifacts cannot be reused by a full build — this is standard Cargo behavior,
not a config bug — so clippy-before-build/test makes Cargo compile the whole
dependency tree **twice** every run. Running the full build first means
clippy (last) can reuse those already-fully-linked artifacts and runs cheaply
by comparison. Net effect: one full cold compile per run instead of two.

One job, four sequential steps (not four parallel jobs): single crate, single
platform (Linux) for now — parallel jobs would only add queueing overhead and
duplicate the dependency-fetch/compile step four times instead of once.
Revisit as a matrix if a second platform or a second crate shows up.

## Gate map
All four steps are **hard gates** — any non-zero exit blocks the run red.
Runs on: `push` to `main`, and `pull_request` targeting `main`. No human
promotion gate (nothing to promote past this check yet). Branch protection on
`main` requiring this workflow green is a follow-up for the human to flip in
GitHub repo settings — not part of the workflow file itself.

## Promotion flow
Not implicated — single environment (CI check), nothing promotes anywhere.

## Reproducibility seams
- **Toolchain pin**: `red-rising/rust-toolchain.toml` pins `1.98.1` (landed —
  edition 2024 needs rustc ≥1.85).
- **Dependency cache**: `Swatinem/rust-cache`, keyed on `Cargo.lock`'s hash
  (landed) — **must also set `cache-on-failure: true`** (revised 2026-10-06).
  Confirmed via the same real run: the action's default
  (`CACHE_ON_FAILURE: false`) skips saving the cache if *any* step in the job
  failed. Since `cargo test` currently fails on a known pre-existing bug
  unrelated to CI, the default would mean the cache **never populates** —
  every run pays the full ~20+ minute cold-compile cost indefinitely, even
  after the dependency compile itself succeeded. `cache-on-failure: true`
  saves it regardless, so the next run (including a rerun of the same PR) gets
  a warm cache despite today's red status.
- **System deps**: Bevy's Linux build needs `pkg-config`, `libwayland-dev`,
  `libudev-dev`, `libasound2-dev`, `libx11-dev`, `libxkbcommon-dev`,
  `libxkbcommon-x11-dev` (confirmed the hard way on the dev host this session)
  — install explicitly via `apt-get` in the workflow, don't assume the runner
  image has them. (Landed.)
- **Headless render**: `cargo test`/`cargo build` must not require a display
  server — confirmed no test instantiates `DefaultPlugins` (headless
  `MinimalPlugins` pattern throughout); no Xvfb needed unless that changes.
- No `dynamic_linking`-specific CI step needed — it's a dev-loop speed
  optimization (see `rpath = true` already in `Cargo.toml`), irrelevant to a
  from-scratch CI build.

## Secrets & config boundary
None needed — no deploy target, no registry credentials, no API keys.

## Evidence of done
A green run (all four steps exit 0) against the PR's head commit, or against
`main` after merge, is the full evidence — there's no running service or
health signal to check past that. For the caching fix specifically: evidence
of done is a **second** run on a warm cache showing materially less wall-clock
time on the `build`/`test` steps than the first cold run, not just the
presence of a saved cache.

## Failure diagnostics
- `cargo test -- --nocapture` output is already captured in the step's own
  log; no extra artifact upload needed (no browser/service traces exist in
  this CLI-only pipeline).
- On failure, GitHub Actions retains the job log by default (90 days) — no
  additional capture step required at this scope.

## Not implicated
Infrastructure, deployment/rollout, and observability — no cloud resources,
no release target, no running service exist yet for this repo.
