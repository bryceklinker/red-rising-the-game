# CI build — runs on `main` and on PRs

Greenfield pipeline design (no prior `.github/workflows`). Scope: build/test/lint
gate only — no deploy, no published artifact. Decided against `.craft-code.yml`'s
existing commands so CI runs exactly what a human already runs locally.

## Artifact strategy
No artifact is produced or stored. This pipeline's only output is a pass/fail
signal on a commit SHA — there is nothing to publish yet (single-player
desktop binary, no distribution channel decided). Revisit when `GDD.md` §11/§12
settles a release target.

## Stage ordering (fail fast, cheapest first)
1. `cargo fmt --check` — no compilation, fails in seconds.
2. `cargo clippy --all-targets --all-features -- -D warnings` — compiles once
   (bins + tests), catches lint + type errors together.
3. `cargo test` — reuses clippy's compiled artifacts via cache; runs the suite.
4. `cargo build` — release-shape sanity build (clippy already compiled
   `--all-targets`, so this mainly guards the default/bin-only build path).

Why one job, four sequential steps (not four parallel jobs): single crate,
single platform (Linux) for now — parallel jobs would only add queueing
overhead and duplicate the dependency-fetch/compile step four times instead of
once. Revisit as a matrix if a second platform or a second crate shows up.

## Gate map
All four steps are **hard gates** — any non-zero exit blocks the run red.
Runs on: `push` to `main`, and `pull_request` targeting `main`. No human
promotion gate (nothing to promote past this check yet). Branch protection on
`main` requiring this workflow green is a follow-up for the human to flip in
GitHub repo settings — not part of the workflow file itself.

## Promotion flow
Not implicated — single environment (CI check), nothing promotes anywhere.

## Reproducibility seams
- **Toolchain pin**: repo has no `rust-toolchain.toml` today — real gap, since
  `edition = "2024"` requires rustc ≥ 1.85 and an unpinned `stable` could drift
  under CI. Implementer must add `red-rising/rust-toolchain.toml` pinning a
  concrete verified-working stable version, committed alongside the workflow.
- **Dependency cache**: key the Cargo registry + `target/` cache on
  `Cargo.lock`'s hash (e.g. `Swatinem/rust-cache`) so CI doesn't recompile all
  of Bevy's ~1000 crates from scratch every run.
- **System deps**: Bevy's Linux build needs `pkg-config`, `libwayland-dev`,
  `libudev-dev`, `libasound2-dev`, `libx11-dev`, `libxkbcommon-dev`,
  `libxkbcommon-x11-dev` (confirmed the hard way on the dev host this session)
  — install explicitly via `apt-get` in the workflow, don't assume the runner
  image has them.
- **Headless render**: `cargo test`/`cargo build` must not require a display
  server — confirm `DefaultPlugins` isn't instantiated by any test (it isn't,
  per the headless `MinimalPlugins` pattern already in use); no Xvfb needed
  unless that changes.
- No `dynamic_linking`-specific CI step needed — it's a dev-loop speed
  optimization (see `rpath = true` already in `Cargo.toml`), irrelevant to a
  from-scratch CI build.

## Secrets & config boundary
None needed — no deploy target, no registry credentials, no API keys.

## Evidence of done
A green run (all four steps exit 0) against the PR's head commit, or against
`main` after merge, is the full evidence — there's no running service or
health signal to check past that.

## Failure diagnostics
- `cargo test -- --nocapture` output is already captured in the step's own
  log; no extra artifact upload needed (no browser/service traces exist in
  this CLI-only pipeline).
- On failure, GitHub Actions retains the job log by default (90 days) — no
  additional capture step required at this scope.

## Not implicated
Infrastructure, deployment/rollout, and observability — no cloud resources,
no release target, no running service exist yet for this repo.
